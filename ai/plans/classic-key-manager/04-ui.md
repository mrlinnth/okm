# Phase 4: Frontend UI

Depends on: Phases 1–3 (all `/classic/keys/*` endpoints working).

### Task [4.1]: Classic Manager view scaffold [DONE]

#### Subtasks

- [ ] Build `app/Views/classic/index.blade.php` extending
      `layouts.master` (per `app/Views/products/index.blade.php`'s
      pattern), replacing the Phase 1 placeholder.
- [ ] Recreate the two-panel layout from `ai/prototype/index.html` /
      `blueprint.md`'s "Classic Manager" screen: "Current server" (left) and
      "Migrate to" (right) panels, directional connector on `lg+`, stacked
      on mobile, using Tailwind + daisyUI classes consistent with
      `app/Views/layouts/master.blade.php`'s existing styling.
  - [ ] Each panel starts with a JSON textarea + Connect button (loose
        client-side validation: parseable JSON, `apiUrl` starts with
        `https://`, shown inline on failure — no backend call yet on
        validation failure).
  - [ ] Migrate-to panel renders disabled with a "Connect a current server
        first" note until the current-server panel is connected.
- [ ] Root Alpine `x-data` holds both panels' state (mirrors the prototype's
      single root `x-data`): `current: {json, connected, label, keys,
    loading, error}`, `migrateTo: {json, connected, label, loading,
    error}`.
- [ ] Connect handler: on the current-server panel, `fetch('/classic/keys/list',
    {method:'POST', body: JSON.stringify({apiUrl})})`; on success set
      `connected = true` and `keys` from the response; on failure show the
      inline error. Migrate-to panel's Connect only needs to confirm
      reachability (reuse the same list call, discard the key list — actual
      keys aren't needed until migrate runs, per requirements).

#### Key Files

- `app/Views/classic/index.blade.php`
- `app/Controllers/Classic.php` (route already exists from Phase 1)

#### Verification

Start the app (`php spark serve` or the project's normal dev command),
visit `/classic`, paste a real or test Outline server JSON, and confirm both
panels connect and the current-server panel lists keys with correctly
formatted usage.

### Task [4.3]: Delete, delete-all, and results [DONE]

#### Subtasks

- [ ] Delete key: daisyUI confirm modal (per requirements — not native
      `confirm()`) → on confirm, `fetch('/classic/keys/delete', ...)` → on
      success remove the key from `current.keys`.
- [ ] Delete all: daisyUI confirm modal → on confirm,
      `fetch('/classic/keys/delete-all', ...)` → show a results panel
      listing deleted/failed counts and full per-key status (matching the
      prototype's "continues after failures" demo), then clear `current.keys`
      to only the still-present (failed-to-delete) keys.

#### Key Files

- `app/Views/classic/index.blade.php`

#### Verification

Manually trigger delete and delete-all against a test server with multiple
keys; confirm the results panel shows accurate deleted/failed counts and
per-key detail.

### Task [4.4]: Migrate, retry, and start over [DONE]

#### Subtasks

- [ ] Migrate button (enabled once both panels are connected): show
      "Migrating…" state → `fetch('/classic/keys/migrate', {sourceKeys:
    current.keys, destApiUrl: migrateTo.json.apiUrl})` → render a per-key
      results list: success (with "renamed from X" when `renamed_from` is
      present) or failed (with the full error text), matching the
      prototype.
- [ ] Retry failed keys: shown only when at least one failed result exists
      → re-`fetch('/classic/keys/migrate', ...)` with `onlyNames` set to the
      currently-failed names → merge the new results into the existing list
      by name, replacing only the retried entries and leaving prior
      successes untouched.
- [ ] Start over (current-server panel): resets both `current` and
      `migrateTo` to their initial empty state.
- [ ] Start over (migrate-results view only): resets `migrateTo` and the
      migrate results, leaving `current` untouched.

#### Key Files

- `app/Views/classic/index.blade.php`

#### Verification

End-to-end manual pass covering the full acceptance criteria from
`requirements.md`: connect both panels, migrate a set of keys including an
intentional name collision and an induced failure, confirm `_2`-style
suffixing and continue-on-error, retry the failed key and confirm prior
successes are untouched, then refresh the page and confirm all state is
cleared.
